# jand 配置化设计

状态：**已在 0.4.1 实现**（main，tag `v0.4.1`）。设计稿基于 `9d0e9ca`（0.4.0），毛仔确认按四层分工实施、版本留在 0.4.x；实现中与原稿不同之处见文末「实现记录」。

## 背景

目前所有规则都写在代码里：Relay 的 15 个参数只有两个能用命令行参数改（`--listen`、`--max-sessions`）；客户端只有 `JAND_RELAY`、`JAND_HOME` 两个环境变量；协作流程（五种消息类型、「双方都 done 才暂停」、暂停后 3 条收尾消息）写死在客户端和 Relay 里。

不同团队的工作方式不同。我们希望程序保持简单，差异通过配置表达。但并不是所有规则都应该能配置。

## 原则

1. **安全底线不可配置。** 能被关掉的安全规则等于没有。
2. **配置按「归谁管」分层。** Relay 由运营者管，本地客户端由使用者管，协作流程由**双方共同**管。
3. **协作流程随邀请走，不放在各自本地。** 两边各配一套本地流程，必然对不上。流程应当像目标一样，由发起方放进邀请，接收方的人在加入时看到并认可。
4. **先少后多。** 目前只有一个团队、一种用法，不知道别的团队会在哪里不同。只开放已经确定需要的；出现第二种真实工作流（例如一对多派发审核）时，再扩展流程模板。
5. **不引入依赖。** 项目目前没有第三方依赖，配置格式用标准库能解析的 JSON。

## 第 0 层：不可配置的安全底线

以下写在程序里，任何配置都不能改变，也不接受来自对方的修改：

- 加密方式、接收码格式与熵、密钥派生。
- 接收码一次性领取；join 后座位锁定。
- 接收方必须由本地用户同意后才 join；`saved` 始终带 `requires_user_approval`。
- 对方的消息、目标、流程说明一律标记为不可信，不能作为本地用户的授权。
- Relay 强制执行的暂停、预算计数、每方收尾消息上限（上限值可由 Relay 配置，但机制本身不可关闭）。
- 「先读再回」拦截（`--anyway` 是每次显式越过，不提供全局关闭）。
- 单文件 10 MiB、单条消息 64 KiB、目标 1 KiB：这些是协议常量，改动需要两端同时升级，按版本号规则处理，不做配置。

## 第 1 层：Relay 配置（运营者）

**文件**：`jand relay --config /etc/jand/relay.json`，或用环境变量 `JAND_RELAY_CONFIG` 指定路径。

**优先级**：命令行参数 > 环境变量 > 配置文件 > 内置默认值。

**辅助命令**：`jand relay --print-config` 输出最终生效的配置。目前配置里没有敏感项；访问令牌实现后只存哈希值。

**校验**：未知字段直接报错，防止拼写错误悄悄失效；数值越界报错，不做静默截断。

```json
{
  "listen": "127.0.0.1:8787",
  "handoff": {
    "max_sessions": 128,
    "max_stored_bytes": 67108864,
    "ttl": "10m",
    "upload_timeout": "2m"
  },
  "chat": {
    "max_chats": 64,
    "max_stored_bytes": 16777216,
    "max_messages": 200,
    "default_budget": 40,
    "max_pause_notes": 3,
    "invite_ttl": "15m",
    "decide_ttl": "30m",
    "idle_ttl": "60m",
    "lifetime": "6h",
    "ended_ttl": "10m",
    "max_wait": "20s"
  },
  "access": {
    "tokens_sha256": []
  }
}
```

- 字段一一对应现有的 `relay.Config`，时长用 Go 的 duration 字符串写法。
- `access` 为共识清单里的 P2 预留：非空时，客户端必须带访问令牌（`X-Jand-Access` 请求头，本地由 `JAND_ACCESS_TOKEN` 或客户端配置提供）。配置里只存令牌的 SHA-256，不存明文。开启后，不带令牌的旧客户端全部被拒，所以这一项要和 P2 一起设计、一起上线，**本稿只预留字段**。
- 对外报告版本：0.4.1 起 `/healthz` 返回 `version`、`handoff` 和 `chat_features`（Relay 支持的对话功能清单）。原稿设想的 `protocol` 字段没有采用：对话的加密标识 `jand-chat/1` 在互不兼容的版本之间一直没变，报出来会误导人以为可以互通，所以改为逐项列出功能。访问控制实现后，再增加一个表示是否开启的字段，不报告令牌数量。

## 第 2 层：本地客户端配置（使用者）

**文件**：`$JAND_HOME/config.json`。`JAND_HOME` 默认为用户配置目录下的 `jand`。

**优先级**：命令行参数 > 环境变量 > 配置文件 > 内置默认值。

```json
{
  "relay": "https://relay.example.com",
  "access_token_file": "~/.config/jand/access-token",
  "out_dir": "./received",
  "chat": {
    "default_budget": 40,
    "recv_wake": ["request", "reply", "delivery"],
    "default_workflow": "pair-dev"
  }
}
```

- `relay` 可以替代每次设置 `JAND_RELAY`，也解决了「发行包里是示例 IP」的首次使用问题：用户配置一次就行，而且真实地址不进仓库、也不进包。
- 访问令牌只能以文件路径的形式配置，不直接写在 config.json 里，这样配置文件可以放心拿给别人看。
- `recv_wake` 只是本机的默认值。不带 `--wake` 调用时生效；传 `--wake ""` 表示这次什么都唤醒。
- 客户端配置只影响本机的行为，**不影响协议，也不影响对方**。

## 第 3 层：协作流程（双方共同）

### 流程文件

发起方本地可以存几套流程，放在 `$JAND_HOME/workflows/<名字>.json`；也可以把示例流程放进仓库的 `workflows/` 目录，供团队共享。发起对话时选用：

```
jand send --chat --workflow pair-dev --goal '...' 交接.md
```

```json
{
  "name": "pair-dev",
  "title": "前后端结对开发",
  "done_rule": "all",
  "pause_notes": 3,
  "budget": 60,
  "kinds": ["progress", "request", "reply", "delivery", "note"],
  "roles": {
    "host": "前端与联调",
    "guest": "后端 API"
  },
  "instructions": "双方主要时间在写代码……（给双方 Agent 看的 Markdown，最多 8 KiB）"
}
```

| 字段 | 含义 | 谁来执行 |
|---|---|---|
| `done_rule` | `all`：双方都 done 才暂停（现状）；`any`：任一方 done 就暂停，用于「一方干活、一方验收」 | Relay |
| `pause_notes` | 暂停后每方可发的收尾消息数，0 到 Relay 上限 | Relay（超过上限时建房被拒绝） |
| `budget` | 首个目标的预算；没给时用本地或 Relay 的默认值 | Relay |
| `kinds` | 本次对话允许的消息类型，只能从内置的五种里选子集 | 双方客户端 |
| `roles` | 双方角色的说明文字 | 仅展示 |
| `instructions` | 给双方 Agent 的流程说明 | 仅展示，属于不可信资料 |

**第一版刻意不开放的：**
- **自定义新的消息类型。** 「先读再回」拦哪些类型、暂停时放行哪些类型，都跟类型的语义绑定。新增一种类型，意味着程序要知道它算不算「要求对方做事」。等真实需求出现，再以内置类型的形式加进来。
- **关闭先读再回、关闭用户同意之类的规则**，见第 0 层。

### 流程怎么传：对话章程

流程不放进交接包的元数据。0.2.x 接收端要求元数据不超过 2048 字节，流程说明放不下。改为在建房时由发起方上传一份加密的**章程**（charter），内容是流程文件加上目标：

1. `send --chat` 建房时，请求体带两部分：
   - **明文**：Relay 需要执行的参数 `done_rule`、`pause_notes`、`budget`。
   - **密文**：完整章程，包括流程和目标，用 `Derive("chat/key")` 加密，附加数据为 `jand-chat/1/{room}/host/charter/0`。
2. 接收方领取交接包后，用邀请令牌取回章程：`GET /v1/chats/{room}/charter`。客户端解密后，**核对章程里的参数与 Relay 报告的明文参数是否一致**。不一致就拒绝并报错：说明 Relay 篡改了参数，或者客户端有 bug。
3. `saved` 事件带上流程名、角色、各项参数和说明全文，接收方的 Agent 原样给人看。**人同意的是「目标加流程」，不只是目标。**
4. 恢复对话时，`propose` 可以附带新的流程参数，按同样方式双方认可。第一版可以先只允许沿用原流程，只改目标和预算。

没指定 `--workflow` 时使用内置的 `default` 流程，行为与 0.4.0 完全一样。

## 测试

- 配置解析：未知字段、越界值、优先级、`--print-config` 打码。
- Relay 用配置文件启动后，各项上限按配置生效（复用现有测试，改由配置构造）。
- 章程：Relay 篡改明文参数时接收方拒绝；章程被替换时解密失败；`done_rule=any` 时任一方 done 即暂停；`pause_notes` 超过 Relay 上限时建房被拒绝。
- 冒烟测试加一个非默认流程的完整对话。

## 实现记录（0.4.1）

- 四层一次实现，版本 0.4.1（毛仔决定不升 0.5）。为此第 3 层做成与 0.4.0 兼容：不带流程时一切照旧；0.4.0 的 Relay 上可以使用默认流程，自定义流程会明确报错并撤回邀请；`done_rule: any` 的对话拒绝不声明支持章程的旧客户端加入（join 请求体 `features: ["charter"]`），避免它收到不认识的 `any_done`。
- `pause_notes` 超过 Relay 上限时，建房直接被拒绝（400，附上限值），而不是截断。这样发起方在发出交接包之前就能发现问题。
- 接收方在领取文件时取回并核对章程，`saved` 事件带上核对后的 `workflow`，以及 Relay 实际执行的 `budget`（顺带解决了「默认预算不显示」）。核对失败时不带 `workflow`，`message` 写明原因；`chat join` 会再核对一次，失败就拒绝加入。
- 访问令牌只预留了字段：Relay 配置 `access.tokens_sha256` 或客户端配置 `access_token_file` 非空时报错，避免有人误以为已经开启了保护。
- `jand config` 显示客户端实际生效的配置及每项的来源；`jand relay --print-config` 显示 Relay 实际生效的配置。
- 示例流程在仓库的 `workflows/`（`pair-dev`、`review`），Relay 配置示例为 `deploy/relay.json.example`。
