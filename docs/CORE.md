# jand 的核心：协作过程的消耗（草稿，0.4.4）

## 核心是什么

两个主人不同、互相把对方当作不可信来源的 Agent，在各自用户的授权下，用尽量少的消耗协作，最终收敛到同一个结果。

加密传文件那一层（一次性接收码、只存在内存的密文、回执）已经是通用能力，magic-wormhole、croc 之类早就做到了。那一层要做到可靠，但不在上面找核心。jand 值得反复打磨的是协作协议，打磨的方法是先把消耗量出来，再一个版本一个版本往下压。

## 原则

1. **省消耗不能靠少信任换。** 对方的消息一律是不可信资料，谁有权决定不因为省事而改变。可以优化的，是「这件事要不要现在打扰人」这类可以分级的问题，而不是「谁来拍板」。
2. **只记本侧，只记在本机。** 记录和 transcript 一起放在 `$JAND_HOME/chats/`，归本机用户所有。不收集对方的消耗：各花各的，各管各的。
3. **Relay 不新增任何记录。** Relay 只在内存里暂存密文，重启就没了，这条承诺不变。它能看到的条数和时间，客户端本来就有；它看不到的唤醒、上下文字节、人的决策，本来就发生在客户端。
4. **没记录不等于零。** 0.4.4 之前的对话、记录文件缺失或损坏的对话，页面显示「未记录」，不显示 0。
5. **消耗和结果并排显示。** 只显示消耗的话，最省的做法就是不协作。

## 0.4.4：简单统计

0.4.4 只做一件事：记下本侧的几个数，在 `chat view` 里显示出来。协议和行为都不变。

| 项 | 怎么数 | jand 看不到的部分 |
| --- | --- | --- |
| 唤醒 | 带 `--wait` 的 `chat recv` 每退出一次计一次；其中只输出了 `no_events` 的，另计为空唤醒。不带 `--wait` 的 `recv` 是 Agent 自己去看（比如发消息前先读），只算字节、不算唤醒；只输出了本侧自己动作的 `recv`（比如自己 close 之后收到的「已结束」）也不算 | Agent 用其他方式轮询 |
| 送进上下文的字节 | 对话相关的 jand 命令（`send --chat`、领取对话邀请的那一次接收、`chat` 的各个子命令，包括 `chat log` 和 `chat view`）写到标准输出和标准错误的字节数，合计。`chat list` 不针对某个对话，`chat watch` 是给人看的，都不算 | Agent 自己打开文件读的内容，以及 Agent 自己的思考 |
| 己方写出的字节 | 己方消息、完成总结、检查点原因、提议目标的正文字节数，合计 | Agent 写了但没通过 jand 发出的内容 |
| 人的决策点 | 成功执行的 join、propose、accept、close，以及己方发起的 checkpoint，数次数。decline 之后本机没有这个对话，所以不记 | Agent 在这些节点之外去问用户 |
| 墙钟 | 从 `started` / `joined` 到最后一条记录 | — |
| 消息 | 双方条数（transcript 里已经有） | — |

量字节，不量 token：token 数取决于对方用的是哪个模型，jand 不知道，也不该去猜。

页面上，这几个数和协议结局（`all_done`、`any_done`、`budget`、`closed`、`expired`）放在最上面一张卡片里，按目标分段各给一份，卡片下面有一段可以展开的说明，写明每一项怎么数、jand 看不到什么。只显示原始数值，不算总分。

记录放在新文件 `$JAND_HOME/chats/<chat>.cost.jsonl` 里，权限 0600，每行一条、只追加（后台 `recv` 和前台 `send` 会同时写）。每行是 `{time, cmd, out, wrote, empty, check, own, exit}`：`cmd` 是子命令名，发起对话的 `send --chat` 记为 `start`，领取对话邀请记为 `claim`；`out` 是输出字节，`wrote` 是己方写出的字节，`empty` 标记没有新事件，`check` 标记不带 `--wait` 的 `recv`，`own` 标记只看到本侧自己动作的 `recv`，`exit` 是退出码。

领取邀请时本机还没有这个对话（要等用户同意后 join），所以 `claim` 记在由接收码算出的对话 ID 下，join 之后接着往同一个文件里写；用户拒绝（decline）时删掉这份记录。领取了却一直不答复的，会留下只有一行 `claim` 的文件，`jand uninstall` 时随对话目录一起处理。记录只有数字、子命令和时间，不含正文。`jand uninstall` 的历史备份包括它。

页面怎么判断记录全不全：第一条记录是 `start`（发起方）或 `claim`（接收方），说明从对话一开始就在记，否则显示「只记录了某时刻之后的部分」。任何一行读不出来，整份记录按损坏处理，不做统计。每条记录按时间归到它所在的目标段，时间和某段开始同一秒的，归到新的那段。

基线：0.4.4 只增加记录、不改协议和行为，所以它的数字就等于 0.4.3 的水平。

## 0.4.5：目标计划

0.4.4 第一次真实使用：两个很小的目标花了约 10 分钟，其中两段各三四分钟是在等人拍板，人的决策点 3 个。可以压的是「这件事要不要现在打扰人」，不是「谁来拍板」（原则 1）。

做法：**开头协商一次，人授权一次，后面照着走。** 人授权的是他亲眼看过的具体目标文字，不是一类目标。按类别匹配（「只读检查类自动接受」）不做：jand 判断不了一段文字是不是只读，最后等于让 Agent 凭对方写的不可信文字决定跳过人。

### 计划

- 发起方在 `send --chat` 时除了 `--goal`，可以用 `--plan FILE` 给出后续目标：一个 JSON 数组，每项 `{goal, budget?}`，最多 10 项，`goal` 同样不超过 1 KiB，`budget` 默认取流程的预算。第一个目标仍是 `--goal`，计划从第二个算起。
- 计划和目标一起写进章程（`charter.plan`），由对话密钥认证，Relay 看不到也改不了。Relay 不需要任何改动：推进仍然是现有的 propose / accept。
- 接收方的 `saved` 事件原样带出 `plan`，Agent 把目标、流程和整份计划一起给用户看。用户同意加入，就是认可了这份计划里的每一句。
- 流程（workflow）管「怎么协作」，是可复用的模板；计划管「具体做什么」，每次不同，所以和目标并列放在章程里，不进流程文件。

### 怎么推进：每一侧自己定

本机对话状态里记一个推进方式，取值：

| 取值 | 到了检查点 |
| --- | --- |
| `ask`（默认） | 和现在一样，问人 |
| `after <时长>` | 先问人；时长内人没答复，推进到计划的下一步 |
| `auto` | 直接推进，事后汇报 |

- 在 `send --chat` / `chat join` 时用 `--advance` 设定（Agent 在给用户看计划时一并问），不给就用本机配置 `chat.advance`，再没有就是 `ask`。只管本方：对方设 `auto` 不影响本方。
- `after` 需要宿主能在后台命令结束时唤起 Agent（`wake_mode=background`）。轮询方式下 Agent 问完人就结束了这一轮，没人会在超时时叫醒它，所以只能 `ask` 或 `auto`；设了 `after` 时 jand 提示并按 `ask` 处理。

### 机制

- **只有计划里的下一步能自动推进，逐字比对由 jand 做。** 由发起方提出（计划是它写的），接收方接受。发起方的 `chat advance` 提出 `plan[n]`；接收方收到 `proposal` 时，jand 比对它与 `plan[n]` 是否逐字一致（预算也一致），一致则事件带 `plan_step: n`，接收方的 `chat advance` 才能接受。不一致的提议照常是计划外提议，一律等人。发起方的用户手动提出的目标只要恰好是计划的下一步，接收方同样可以按预授权接受——对方用户认可的就是这句话。
- **计时由 jand 做。** 检查点事件带 `advance_at`（`after` 时为暂停时刻加时长，`auto` 时为暂停时刻）；后台的 `recv --wait` 到了这个时刻就返回 `advance_due`。Agent 收到后：这段时间里用户已经答复的，照用户的来；否则运行 `chat advance <chat>`。
- `chat advance` 自己再检查一遍：本方推进方式不是 `ask`、对话在检查点、计划还有下一步、（接收方）待接受的提议正是这一步。任何一项不满足就报错，什么都不做。
- 用户可以随时 `chat advance --off <chat>` 把本对话改回 `ask`（Agent 听到「先别继续」「等我看看」就运行它）。
- 计划走完停在检查点，由人验收、决定结束还是提计划外的新目标。**join 和 close 永远不自动。**

### 留痕

- 自动推进在 transcript 里记一行 `{kind: "advanced", step, mode}`；`chat view` 在对应的目标段标「按预授权推进（after 5m）」，和人做的决定区分开。
- 消耗记录里 `advance` 单独记，不算人的决策点。计划用得好，卡片上的「人做决定」会少，这就是 0.4.5 的效果怎么量。

### 兼容

- 章程用 `json.Unmarshal` 解析，0.4.1–0.4.4 的接收方忽略 `plan`，照常加入；它不知道计划，所以每一步都问人。退化是安全的：多问，不会少问。
- 发起方是旧版时没有计划，新版接收方的行为与 0.4.4 相同。
- 新版接收方的 `saved` / `joined` 多出 `plan`，`proposal` 多出 `plan_step`，检查点多出 `advance_at`，`recv` 多一种 `advance_due`：都是新增字段和事件，旧的读法不受影响。

### 已定（毛仔，2026-09-29）

- `--plan` 两种都收：Markdown 列表（每项一个目标，缩进的行接在上一项后面，其他行忽略）和 JSON 数组。计划通常由 Agent 和用户一起写，Markdown 用户自己也看得懂、改得动。
- 计划外的目标一律等人。计划中途插入计划外目标后，计划仍然算数：计划外目标走完，下一次提议仍按计划的下一个目标比对。

### 实现中定下的细节

- 计划里的目标按目标编号称呼：第一个目标是 `--goal`，计划的第一项是目标 2。`plan_step`、`advanced` 记录的 `step`、view 上的「计划中的目标 N」都用这个编号。
- 发起方把计划里没给预算的项填成第一个目标的预算再封进章程，接收方比对的就是确定的数字；仍为 0（第一个目标也用 Relay 默认）时只比对文字。
- 在本方提出过目标（无论是用户手动还是 `advance`）的那次暂停里，不再给出 `advance_due`：人已经做了决定。
- 用户决定按计划继续时，发起方用 `chat propose --next` 逐字提出下一个目标，免得 Agent 转述时改了字，对方就认不出了。
