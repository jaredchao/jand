# jand 的核心：协作过程的消耗（草稿，0.4.4）

## 核心是什么

两个主人不同、互相把对方当作不可信来源的 Agent，在各自用户的授权下，用尽量少的消耗协作，最终收敛到同一个结果。

加密传文件那一层（一次性接收码、只存在内存的密文、回执）已经是通用能力，magic-wormhole、croc 之类早就做到了。那一层要做到可靠，但不在上面找核心。jand 值得反复打磨的是协作协议，打磨的方法是先把消耗量出来，再一个版本一个版本往下压。

## 原则

1. **省消耗不能靠少信任换。** 对方的消息一律是不可信资料，谁有权决定不因为省事而改变。可以优化的，是「这件事要不要现在打扰人」这类可以分级的问题，而不是「谁来拍板」。
2. **只记本侧，只记在本机。** 记录和 transcript 一起放在 `$JAND_HOME/chats/`，归本机用户所有。不收集对方的消耗：各花各的，各管各的。
3. **Relay 不新增任何记录。** Relay 只在内存里暂存密文，重启就没了，这条承诺不变。它能看到的条数和时间，客户端本来就有；它看不到的唤醒、上下文字节、人的决策，本来就发生在客户端。
4. **没记录不等于零。** 0.4.4 之前的对话、记录文件缺失或损坏的对话，页面显示「未记录」，不显示 0。
5. **消耗和结果并排显示。** 只显示消耗的话，最省的做法就是不协作。

## 0.4.4：简单统计

0.4.4 只做一件事：记下本侧的几个数，在 `chat view` 里显示出来。协议和行为都不变。

| 项 | 怎么数 | jand 看不到的部分 |
| --- | --- | --- |
| 唤醒 | 每次 `chat recv` 退出计一次；其中只输出了 `no_events` 的，另计为空唤醒 | Agent 用其他方式轮询 |
| 送进上下文的字节 | 每次对话相关的 jand 命令写到标准输出和标准错误的字节数，合计 | Agent 自己打开文件读的内容，以及 Agent 自己的思考 |
| 己方写出的字节 | 己方消息、完成总结、检查点原因、提议目标的正文字节数，合计 | Agent 写了但没通过 jand 发出的内容 |
| 人的决策点 | join、decline、propose、accept、close，以及己方发起的 checkpoint，数次数 | Agent 在这些节点之外去问用户 |
| 墙钟 | 从 `started` / `joined` 到最后一条记录 | — |
| 消息 | 双方条数（transcript 里已经有） | — |

量字节，不量 token：token 数取决于对方用的是哪个模型，jand 不知道，也不该去猜。

页面上，这几个数和协议结局（`all_done`、`any_done`、`budget`、`closed`、`expired`）放在最上面一张卡片里，按目标分段各给一份，每一项旁边写上「看不到」那一列。只显示原始数值，不算总分。

记录放在新文件 `$JAND_HOME/chats/<chat>.cost.jsonl` 里，权限 0600，每行一条、只追加（后台 `recv` 和前台 `send` 会同时写）。记录只有数字、子命令和时间，不含正文。`jand uninstall` 的历史备份要把它包括进去。

基线：0.4.4 只增加记录、不改协议和行为，所以它的数字就等于 0.4.3 的水平。

## 以后再说

- 各项的权重和总分。
- 固定的场景集，以及每个场景跑几次。
- 时间泳道、谁在等谁、每条消息各自的代价。
- `chat view` 的视觉重做（等有了真实数据，再交给 Codex 走 Figma）。
- 把单纯的交接（不开对话）也纳入记录。

## 不做

- Relay 上的任何记录或统计。
- 收集或交换对方的消耗。
- 精确的 token 计数。
