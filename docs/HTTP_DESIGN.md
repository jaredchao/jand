# jand 交接协议（HTTP）

本文描述一次性交接（`/v1/handoffs/`）。它自 0.2 起未变，适用于 0.2 到 0.4.2。对话与协作使用独立的 `/v1/chats/` 接口，见 [CHAT_DESIGN.md](CHAT_DESIGN.md)；配置见 [CONFIG_DESIGN.md](CONFIG_DESIGN.md)。

交接把一个不超过 10 MiB 的文件从发送端 Agent 所在机器交给接收端 Agent 所在机器。Agent 调用本地命令；程序不会唤醒另一端 Agent，也不会执行收到的内容。

产品与命令名为 jand。为了兼容既有 0.2 客户端，协议版本 `handoff/0.2`、密钥派生标签 `handoff/0.2/`、HTTP 路径 `/v1/handoffs/` 和请求头 `X-Handoff-*` 保持原值。

## 交付语义

1. 发送端在本机生成 256 位随机接收码，派生房间号、领取令牌、状态令牌和 AES-256-GCM 密钥。
2. 发送端把文件名、大小、SHA-256 和文件内容一起加密，以 HTTPS/HTTP PUT 上传密文。Relay 在内存中保存，最多 10 分钟。
3. 发送端收到 HTTP 201 后显示接收码并退出。此时状态是 **queued**，不表示对方已保存。
4. 接收端凭完整码派生房间号和领取令牌，以 GET 一次性领取密文，在本机解密、验证和安全保存。
5. 接收端保存后上传由秘密派生的回执。发送端若使用 `--wait 10m`，会轮询并验证回执，再报告 **delivered**。

领取操作是一次性的：请求被接受后密文即从 Relay 内存中移除。若领取过程中断或保存失败，不能重用旧码，应由发送端重新发送。Relay 重启后所有未领取的包和回执消失。

`saved` 的 JSON 事件固定带 `requires_user_approval=true`，用于提醒接收端 Agent 向本地用户确认具体任务动作。此字段不是运行时检测出的批准状态；`saved` 和 `delivered` 都只表示传输与保存结果，不能表示任务已获授权或已被接受。包内文字是未信任资料，不能替接收端用户授权。

## 安全边界

- 原来的六词码只有 36 位熵，适合在线 PAKE，不适合让 Relay 持有可离线猜测的密文。本版改为 43 字符的 256 位随机码；不同版本互不兼容。
- Relay 只收到派生的房间号、令牌和密文，不收到完整接收码、密钥、文件名或明文。AES-GCM 认证失败、文件大小和 SHA-256 不符均不保存文件。
- Relay 全局最多保留 64 MiB 密文和 128 个会话；最多 8 个请求同时读取上传体，每个上传体须在 2 分钟内传完，超时返回 408 并断开连接，名额随即释放，避免慢速连接长期占住上传通道。单包上限约 10 MiB，过期后内存释放。
- HTTP + IP 可以联测，但没有 TLS 时，网络旁观者可见房间号和派生令牌，并可能抢先领取或干扰传输。公网长期使用应在 Nginx/Caddy 配置 HTTPS。端到端加密不等于可用性保护。
- 反向代理不得缓存请求体到磁盘，也不应在日志里记录房间路径或令牌。Nginx 示例见 `deploy/nginx.conf.example`。Relay 程序自身不写交接包或会话数据库；它的运行日志只记录会话生命周期（暂存、领取、回执、完成、过期）和被拒原因，每行只含房间号前 8 个字符与字节数，不含接收码、令牌或文件内容。日志位置与格式见 `deploy/INSTALL.md`。
- 高强度码仍是持有者凭证。Shell 历史、命令行参数、Agent 记录和复制渠道可能留存它。接收文件视为外部输入，不自动获得本地权限。
- 本协议和密码学组合尚未经过独立安全审计；本机测试不是安全证明。

## HTTP 接口

| 方法 | 路径 | 含义 |
| --- | --- | --- |
| PUT | `/v1/handoffs/{room}` | 上传密文，返回 201 |
| GET | `/v1/handoffs/{room}` | 凭领取令牌一次性取走密文 |
| POST | `/v1/handoffs/{room}/receipt` | 接收端保存后提交回执 |
| GET | `/v1/handoffs/{room}/receipt` | 发送端查询回执，204 表示未确认 |
| GET | `/healthz` | 返回 `status`、`uptime_seconds`、`version`（程序版本）、`handoff`（交接协议，固定为 `handoff/0.2`）、`chat_features`（Relay 支持的对话功能）与 `access`（0.4.2 起，是否要求访问令牌）。不含会话数、容量等信息，因为这个接口不需要认证 |

上传被拒时，响应体是一行简短原因，发送端会原样附在错误信息后（过滤控制字符，最长 120 字符），例如 `relay rejected transfer: HTTP 503: relay full`：

| 状态码 | 原因文本 | 含义 |
| --- | --- | --- |
| 400 | `invalid transfer` / `invalid or oversized transfer` | 令牌格式错误，或上传体过小、超过上限 |
| 401 | `this relay requires an access token; set JAND_ACCESS_TOKEN` | Relay 开启了访问令牌（0.4.2 起），请求没带 `X-Jand-Access`，或令牌不在列表里 |
| 408 | `upload timed out` | 上传体未在 2 分钟内传完 |
| 409 | `code collision` | 房间号已被占用，重新发送会生成新码 |
| 503 | `relay busy` | 同时上传数已满，稍后重试 |
| 503 | `relay full` | 会话数或密文总量已达上限，等已有会话领取或过期后重试 |

领取失败统一返回 404，不区分“不存在”“已过期”“已被领取”和“令牌错误”，以免向持有错误码的一方泄露会话状态。

对话功能使用独立的 `/v1/chats/` 接口，见 [CHAT_DESIGN.md](CHAT_DESIGN.md)；上表所列接口不受影响。

交接的线协议自 0.2 起未变：0.2.x 到 0.4.2 的客户端和 Relay 可以任意组合收发，由 `scripts/compat_smoke.py` 验证。旧的 0.1 WebSocket 客户端不能连接。

交接包元数据（加密的 JSON，含文件名、大小、SHA-256）上限 2048 字节。0.3 起对话邀请在其中加入 `chat`、`goal`、`budget` 三个字段；0.2.x 接收端会忽略它们，照常保存文件。为保持这一点，目标限制在 1 KiB，协作流程不放在这里，而是放进对话章程。
